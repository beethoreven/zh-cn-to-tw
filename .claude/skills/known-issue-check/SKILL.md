A persistent, growing checklist of bug patterns to actively check for in code before considering a change complete. This file is meant to accumulate items over time — every time a new *class* of bug is found and fixed (not just a one-off typo), add a new numbered item here so future work catches the same pattern before it ships, instead of re-discovering it the hard way.

## How to use (checking mode)

When invoked to check code: go through every item below against the code in scope (a diff, or specific files named by the user). For each item, actually read the relevant code and reason about it — don't just grep for a keyword and call it done. Report concrete findings as `file:line — what's wrong — why`. If an item doesn't apply to this codebase/language, say so briefly rather than skipping silently. If nothing is found, say so explicitly rather than staying quiet.

## How to use (adding mode)

When invoked to add a new item (e.g. "/known-issue-check add ..." or the user describes a bug just fixed): write a new numbered section following the same structure as the existing ones — a short name, the general pattern (not just the one instance), a concrete example from the session that motivated it, and what to look for when checking. Append it to the Checklist section below; don't renumber or rewrite existing items.

## Checklist

### 1. Race conditions: async completion torn down before it actually completes

**Pattern**: An asynchronous operation (network send, file write, animation, any callback-based API) is followed *immediately* by cleanup/teardown/cancellation of a resource that the async operation still needs — without waiting for that operation's own completion handler to fire first. The bug is invisible in code review unless you specifically trace *when* each callback actually runs relative to the surrounding cleanup code, because the code often reads top-to-bottom as if it were synchronous.

**How to check**: For every asynchronous call (anything taking a completion handler, delegate callback, `async`/`await`, Combine/Promise chain, etc.), ask: "does anything on the next line (or any line that runs before this callback fires) tear down, cancel, or deallocate state this callback needs?" If cleanup and the async operation both touch the same resource (a connection, a file handle, a window, a subprocess), the cleanup must be sequenced to run *after* the async operation's own completion, not merely *after the call that started it*.

**Concrete example (zh-cn-to-tw-mac, `GoogleDesktopSignIn.swift`, 2026-08-10)**: A one-shot local HTTP listener parsed an OAuth callback, then called `respond(on: connection, success: true)` (which internally calls `connection.send(...)`, an *async* operation) immediately followed by `finish(.success(token))` on the next line. `finish()` called `tearDown()`, which called `connection.cancel()` on the *same connection* the `send()` was still in flight on. Depending on timing, the cancel could win the race and kill the connection before the HTTP response bytes actually reached the browser — the browser saw `ERR_EMPTY_RESPONSE`, even though the token had already been correctly extracted and handed off in-process (that part was synchronous and unaffected, which is exactly what made this confusing to diagnose: one side of the operation "worked" and the other silently didn't). Fix: `respond()` was changed to take a completion callback, and `finish()` was moved to run *inside* that callback (i.e., after `connection.send`'s own completion handler had already run), so teardown only happens once the response is verifiably out the door.

### 2. Race conditions: a stale/delayed async callback clobbers newer state

**Pattern**: A long-lived object hands out a completion/delegate callback tied to some resource generation N (a process, a connection, a request). The callback closure updates shared state (`self.foo = ...`) unconditionally when it fires. If generation N is replaced by generation N+1 (a restart, a retry, a reconnect) *before* generation N's callback actually fires — because delivery of that callback was delayed for any reason (OS scheduling, process-reaping latency, network jitter) — the stale callback still fires eventually and blindly overwrites state that generation N+1 has already correctly set, even though N+1 is the one that's actually current and healthy. This differs from item #1: it's not about tearing down something *too early*, it's about a callback from the *previous* instance firing *too late* and stomping on the *current* instance's already-correct state. The system can look intermittently "fine, then randomly broken" because generation N+1 briefly worked before N's callback landed.

**How to check**: For every long-lived object that can be recreated/restarted (a subprocess wrapper, a reconnect loop, a retry-with-new-attempt pattern), check whether its completion/termination/delegate callbacks compare against the *current* live instance before mutating shared state — not just whether they *have* a callback. Look for `self?.foo = ...` (or unconditional `self.foo = ...`) inside a callback that was registered against a specific instance (a `Process`, `NWConnection`, `URLSessionTask`, etc.) without an identity check (`self.currentThing === thisSpecificThing`) guarding the mutation.

**Concrete example (zh-cn-to-tw-mac, `OCRServiceManager.swift`, 2026-08-10)**: `start()` creates a `Process`, and both its `readabilityHandler` (reads the port it reports on stdout) and `terminationHandler` (fires on exit) closures unconditionally set `self.port`/`self.process`. When the ocr-service subprocess restarted (idle-timeout self-exit, then the health-check timer respawned a new one on a new port), the user watched the app get stuck on a loading screen even though `ps`/`curl /health` proved the *new* process was alive and healthy. Root cause: the *old*, already-dead process's `terminationHandler` fired late (after the new process had already started and correctly reported its own port), and unconditionally reset `self.port = nil` / `self.process = nil`, wiping out the new process's already-correct state. Fixed by capturing `let process = Process()` locally and checking `self.process === process` inside both callbacks before mutating anything, so a callback from a superseded generation is a no-op.

**Concrete example 2 (zh-cn-to-tw-web, `script.js`'s `pollJob`/`pollReview`, 2026-08-18)**: Same pattern, different technology — no `Process`/`self.foo =` in sight, but the identical shape. Both polling functions run a `setInterval`-driven `async tick()` that calls `authedFetch` then unconditionally acts on the response (`renderFindings(review.findings)`, `clearInterval`, etc.) with no check on whether this particular `tick()` invocation still belongs to the current polling "generation." A user's Stage 2 review got interrupted mid-run because the backend happened to be redeploying; a `tick()` had already sent its `fetch` before the interruption was detected, so the "old" in-flight request was still pending when the user clicked "重試" (retry), which called `pollReview(reviewId)` again — starting a fresh interval, but not invalidating the *first* interval's already-dispatched-but-not-yet-resolved fetch. Once the backend finished redeploying, that stale request finally resolved with `status: "done"` (now stale-but-still-true information) and called `renderFindings()` again, wiping `findingsList.innerHTML` and rebuilding every checkbox from scratch — silently un-checking whatever the user had already selected in the new, current render, roughly 3 seconds after they'd checked it. No error, no visual glitch at the moment of the click — only a delayed, unexplained reset that looked like the checkbox itself was broken. Confirmed via frame-by-frame analysis of a screen recording (checked at ~2s, reset at ~5s — matching the 5-second poll interval) and then reproduced directly by monkey-patching `authedFetch`/`renderFindings` in a live page to simulate a slow first response racing a fast second one. Fixed identically to the Swift case in spirit: `let myGeneration = ++pollGeneration` (module-level counter) captured at the top of `pollJob`/`pollReview`, with `if (myGeneration !== pollGeneration) return;` guarding the response-handling code inside `tick()` right after the `await` — a stale generation's response is now a no-op instead of a silent state clobber. The lesson generalizes past Swift/`Process`: *any* `setInterval`/`setTimeout` + `async` polling loop that can be restarted (retry buttons, reconnect logic, "try again" flows) needs this same generation guard, not just OS-level subprocess/connection wrappers.

### 3. Using a short-lived third-party identity token as a long-lived bearer credential

**Pattern**: A backend authenticates requests by directly verifying a third-party identity provider's token (Google/Microsoft/Apple ID token, Firebase token, etc.) on *every* API call, instead of exchanging it once for the application's own session credential. These provider tokens are deliberately short-lived (Google ID Tokens: ~1 hour) because they're designed to prove identity *at a moment in time*, not to authorize an entire ongoing session — but nothing in the code stops you from treating one as if it were a session token, and it will *work* in every quick manual test (login → click around → done in a few minutes), so the bug only shows up in real usage once a session runs longer than the token's lifetime. The failure mode is worse than a simple logout: any in-flight, already-expensive work (a paid LLM call, a long batch job) that finishes *after* the token expires can end up unable to save its own result, because the "save"/"apply" call is the one that gets the 401 — the work already happened and already cost money, but there's no way to persist it under the now-invalid credential.

**How to check**: For any endpoint/route that verifies a provider token (looking for calls like `verify_oauth2_token`, `admin.auth().verifyIdToken`, `jwt.decode` against a third-party issuer) on every single protected request rather than once at a dedicated login/exchange endpoint: ask "what's this token's actual TTL, and what's the longest realistic single session in this app (including retries/backoff/long batch jobs)?" If a session can plausibly outlive the token, that's the bug. Also check the client side: does anything treat a 401 from an expired-but-previously-valid credential the same as "never logged in" — e.g., does a poll loop watching a background job/task treat a 401 as "the job doesn't exist" and give up, potentially causing the user to think a paid-for result is gone and re-run (and re-pay for) the same work?

**Concrete example (zh-cn-to-tw-backend / zh-cn-to-tw-web, 2026-08-10)**: The frontend stored the raw Google ID Token from Google Identity Services / the desktop system-browser login flow in `localStorage` and sent it as the `Authorization: Bearer` header on every API call, and `require_auth` called `verify_google_id_token` (a full Google signature/expiry/audience check) on every single protected route. Browser mode partially papered over this with a 45-minute `google.accounts.id.prompt()` silent-refresh timer, but desktop mode had no refresh mechanism at all — a long Stage-1/review session (easily pushed past an hour by quota-retry backoff, which this project's own pipeline does) would silently start 401ing on every call once the token hit ~60 minutes old, including the "套用" (apply) button *after* the review's LLM cost had already been paid and the result computed server-side. Worse, the job/review polling loops treated that 401 identically to "job not found," which could make a healthy, already-finished backend job look like it had vanished. Fixed by adding an application-owned `sessions` table (`auth_utils/sessions.py`): the Google ID Token is now verified exactly once, at a dedicated `POST /auth/login` endpoint, which mints an opaque session token with a *sliding* expiry (renewed on every use, so it effectively never expires during active use) that the frontend uses for everything afterward. Revocation (admin deactivating a user) still takes effect within seconds regardless, because that's enforced by a separate live whitelist lookup on every request — decoupling "is this credential valid" from "is this account currently permitted" turned out to be the key structural move.

### 4. A dynamically-assigned endpoint captured once, then never updated when the provider restarts

**Pattern**: A component obtains the address of a dependency at startup — a port assigned by the OS, a container's ephemeral IP, a presigned URL, a session-scoped worker ID — and bakes it into something that is computed *once* and never recomputed: a `const` at module load, a query string in a URL, a config object built at boot. This works perfectly until the dependency restarts and comes back at a *different* address. The consumer keeps talking to the old address forever, and the failure looks nothing like "the dependency restarted": it's a bare connection error against an address that nothing is listening on, while the dependency itself is provably alive and healthy at its new address. Diagnosing it from the error message alone is close to impossible, because every layer reports the truth about *its* view — the process list shows the service running, a manual `curl` to the new port works, and only a side-by-side comparison of "address the client is using" vs "address the service is actually on" reveals the mismatch. The trap is that the initial capture is usually correct and stays correct through all short manual tests; it only breaks after the first restart.

**How to check**: For any address/handle obtained at runtime from a restartable dependency, find *where it is stored* and ask "if the dependency restarts and gets a new value, what recomputes this?" Specifically look for: a `const`/`final`/`readonly` initialized from a startup-time value; a value embedded in a URL query string or template that would require a full reload to change; a config struct populated once in `main()`/`init()`. The fix is usually to resolve the address *at call time* through a function, and to give the owner of the dependency a way to push updates to consumers (or have consumers re-read a mutable holder) — not to reload/restart the consumer, which typically destroys user state. Also check the reverse direction: when the dependency shuts down deliberately, is the consumer's cached address *cleared*, or left pointing at a dead endpoint so the next call fails confusingly instead of triggering a clean restart?

**Concrete example (zh-cn-to-tw-mac / zh-cn-to-tw-web, 2026-08-11)**: The Mac shell launched the local OCR subprocess with no fixed port (deliberately, to avoid a stale process squatting a hard-coded one), read the OS-assigned port from the child's stdout, and passed it to the embedded web UI as a `?ocrPort=` query parameter, which `script.js` read once into `const DESKTOP_OCR_BASE`. The service self-terminated after 30 minutes idle and a health-check timer respawned it on a *new* port; the page kept POSTing to the old one. The user reported "無法連接伺服器" while `lsof` showed the service listening happily on 51993 and the page's console showed it calling 51655. Worse, the app's manual refresh button only copied the port across `if let currentPort = ocrManager.port` — which is `nil` precisely when the service is dead — so refreshing reloaded the page with the *same dead port* and appeared to do nothing. Fixed by resolving the base URL through a `desktopOcrBase()` function reading a mutable `window.__OCR_PORT__` that the shell pushes via `evaluateJavaScript` on every port change (deliberately *without* reloading the page, so in-progress user state survives), pushing `null` when the service stops so a dead address is never retained, and re-pushing after `didFinish` since a page load wipes `window`.

### 5. A resource-hungry helper process kept alive far beyond its actual window of use

**Pattern**: A helper process/service that is only needed for one narrow step of a workflow is instead started at application launch and kept running for the whole session, because "it might be needed again" or simply because startup was the convenient place to put it. This is easy to miss because it isn't a correctness bug — everything *works*; it just quietly holds a large allocation (ML model weights, a browser engine, a JIT'd runtime, a big cache) for hours while doing nothing. It gets actively harmful when someone later notices the memory and bolts on an *idle self-shutdown* without removing the *supervisor's auto-restart* — the two then fight: the service exits to free memory, the supervisor's health check respawns it seconds later, and the memory is never actually reclaimed while the churn generates a stream of restarts (which is exactly the soil item #4 grows in). A tell-tale sign of this fight is an idle timeout measured in tens of minutes paired with a health check measured in tens of seconds.

**How to check**: For every long-lived child process or heavyweight singleton, ask "what fraction of a typical session is this actually doing work?" If the answer is "one step of many," its lifetime should be tied to that step, not to the application's. Then check for the fight: if the service can shut *itself* down (idle timeout, max-requests, memory ceiling), does anything else unconditionally restart it on a timer? If both exist, the shutdown is decorative — reconcile them by picking one owner of the lifetime. When moving to on-demand start, check three follow-on hazards: (a) does any UI gate rendering on the service being up (a loading screen waiting for a service that now never starts unprompted)? (b) is there a *readiness* check before first use, distinct from merely having an address — many servers print/publish their port *before* they begin accepting connections, so "I know the port" does not mean "I can connect"; (c) is the expensive initialization surfaced to the user as a named step, or does it hide inside the first real request and look like a hang?

**Concrete example (zh-cn-to-tw-mac / zh-cn-to-tw-ocr-service, 2026-08-11)**: A PaddleOCR service was started at app launch and kept alive all session, though it is only used for the OCR sub-step of Stage 1 (not Stage 1 refinement, not Stage 2 proofreading, not download or login). Measured: 6 MB at process start, 26 MB after imports, **393 MB** once models load — held for the entire session. A 30-minute idle self-shutdown had been added, but the shell's 30-*second* health-check timer respawned it immediately, so memory was reclaimed for ~30 seconds per cycle while every cycle handed out a fresh port. Fixed by tying lifetime to use: the web UI asks the shell to start the service immediately before an OCR run and to stop it in a `finally` once the pages are retrieved, and the periodic auto-restart was deleted. All three follow-on hazards were live and had to be fixed too — the `WebView` had been gated on `stableOcrPort != nil` (which would have hung forever on "本機 OCR 服務啟動中" once nothing started the service at launch); the port is printed *before* `app.run()` begins listening, so a `/health` readiness poll was needed before sending the first PDF; and the 25-second model load had been implicit inside the first page's OCR call, showing "辨識中（第 0/N 頁）" frozen for 25 seconds, so it was hoisted into an explicit `preload()` reported as its own `phase` the UI names out loud.

### 6. A pipe read handler that spins forever once the writer closes (EOF not handled)

**Pattern**: Code reads a subprocess's output through a pipe using an event-driven readability callback (`FileHandle.readabilityHandler`, `epoll`/`kqueue` readiness, `select()` loops, some `on('readable')` handlers). When the writing end closes — the child exited — the file descriptor becomes *permanently readable* (that's how EOF is signalled at the readiness layer), so the runtime calls the handler over and over, forever, as fast as it can. A handler written as "if there's no data, just return" looks perfectly defensive but is exactly the bug: returning early without *unregistering* the handler leaves the descriptor still readable, so it is immediately called again. There is no error, no crash, no log line — only a core pegged at 100%. It is easy to ship because it requires the child to die to manifest, and dying children are usually tested as "does it restart?" not "what does CPU do afterwards?". If the parent restarts the child, each dead generation leaves behind its own spinning handler, so usage climbs in multiples and looks like a leak with no obvious allocation.

**How to check**: For every readability/readable callback attached to a pipe, socket, or file descriptor whose peer can close, find the zero-length-read branch and confirm it *unregisters* (`handle.readabilityHandler = nil`, remove from the event loop, close the fd) rather than merely `return`ing. Then check the restart path: when a new child is spawned and a new pipe assigned to the same field, is the *previous* pipe's handler explicitly cleared, or does the old one keep running because only the reference was overwritten? A quick empirical test settles it: measure the parent's CPU while the child is healthy, kill the child, and measure again — a jump to ~100% of one core that never subsides is this bug.

**Concrete example (zh-cn-to-tw-mac, `OCRServiceManager.swift`, 2026-08-11)**: `stdout.fileHandleForReading.readabilityHandler` parsed the port line the OCR subprocess prints, guarding with `guard !data.isEmpty, let text = ... else { return }`. Once the subprocess exited, `availableData` returned empty forever and the closure was re-invoked in a tight loop. Controlled measurement: parent app at **0.0% CPU** with the child healthy, **96%** within seconds of `kill -9` on the child, never recovering; a session left open ~5 hours across several idle-restart cycles measured **283%** (multiple stacked spinners). Fixed by treating the empty read as EOF and clearing the handler: `guard !data.isEmpty else { handle.readabilityHandler = nil; return }`. Re-running the same controlled test afterwards showed 0.0% → 0.0%.

### 7. Configuration read at module import time, before the loader that populates it has run

**Pattern**: A module reads configuration directly from the process environment at *import* time (a module-level `X = os.environ.get("X")`, a `static final` initializer, a top-level `const`), while the mechanism that *populates* that environment — `load_dotenv()`, a config bootstrap, a secrets fetch — runs inside some other module that happens to be imported later. Python (and any language with import-order-dependent initialization) will happily evaluate the reader first, yielding an empty value. The damage depends entirely on what the code does with "empty": if it raises, you find out immediately; if it *falls back to a default*, you get silent, plausible-looking wrong behaviour, and the fallback is often a local/dev resource that still works well enough to pass a smoke test. This is especially dangerous when the fallback is a different *data source*, because subsequent reads and writes go somewhere real — just not the place you think — and any comparison you run to "verify" the data will compare that wrong source against itself and appear to confirm everything is fine.

**How to check**: Grep for environment/config reads at module scope (not inside a function) and, for each, trace whether the populating call is guaranteed to have run first. The structural fix is to have exactly one module own config loading and have every other module read *through* it (`from configs import config; config.DATABASE_URL`) rather than re-reading the raw environment. Then check the failure mode: when a critical setting is missing, does the code raise loudly, or silently substitute a default? Anything that selects a *data source* (database URL, storage backend, API base) should raise, never fall back. Finally, be suspicious of any verification step that reads through the same possibly-misconfigured layer it is meant to be checking.

**Concrete example (zh-cn-to-tw-backend, `db_utils/connection.py`, 2026-08-10)**: `DATABASE_URL` was read via `os.environ` at module level in `db_utils/connection.py`, which `app.py`'s import chain reached *before* `configs/config.py` ran `load_dotenv()`. With a perfectly correct `.env`, the value came back empty and the code silently fell back to SQLite. In the PyInstaller-frozen build this quietly created a throwaway `_internal/usage.db`. It also produced a false verification: a check intended to confirm "Neon already has all 568 rows" was in fact comparing the local SQLite file against itself, so the migration looked complete when 436 rows were actually missing. Fixed by making `configs/config.py` the sole reader of `DATABASE_URL` and having `get_conn()` raise `RuntimeError` when it is unset, with the SQLite path removed entirely rather than left as a fallback.

### 8. Failure paths that are silent because the diagnostic hook was never registered

**Pattern**: A framework reports errors *only* through an optional delegate/listener/callback that the application never implemented, so failures produce no exception, no console output, and no visible state change — just a blank screen or a no-op. Because nothing is thrown, normal defensive habits (try/catch, checking return values) don't help; the code path completes "successfully" from the caller's point of view. Debugging then starts from zero information, and time gets spent on plausible-but-wrong hypotheses. The general lesson is that for any component whose error channel is opt-in, *registering the error channel is part of correctly using the component*, not an optional nicety to add later when something breaks.

**How to check**: For each framework object with optional delegates/observers (web views, media players, background transfer sessions, file coordinators, IPC channels), list the failure-reporting members of that protocol and confirm at least a logging implementation exists for each. Ask specifically: "if this operation fails right now, through what channel would I learn about it?" If the honest answer is "I wouldn't," implement the hook before writing any more feature code against that component — and keep it permanently, not as temporary debug scaffolding.

**Concrete example (zh-cn-to-tw-mac, `WebView.swift`, 2026-08-11)**: The `WKNavigationDelegate` implemented no failure methods, so a `loadFileURL` that failed left the view stopped at `about:blank` with zero indication of why. Implementing `didFailProvisionalNavigation`, `didFail`, and `didFinish` — purely to print — was what finally surfaced `WebKitErrorDomain code 101`, which led to the real root causes (see items #9 and #10). A second, compounding factor was that the app's own `print()` output wasn't reaching the log at all (see item #13), so the first attempt to add diagnostics appeared to produce nothing and briefly suggested the code wasn't running. These three delegate methods were kept permanently rather than removed once the bug was fixed.

### 9. URL values that carry hidden structure and get silently mangled by "normalizing" APIs

**Pattern**: A URL obtained from a framework is not always the flat absolute string it appears to be — it can internally be a *relative string plus a base URL*, and APIs that decompose and reassemble it can drop the base, yielding a scheme-less relative path that fails in ways that don't mention URLs at all. The value passes every cheap sanity check on the way (it prints plausibly, `isFileURL` reports true), so the corruption is invisible until whatever consumes it fails with a generic error. A closely related trap in the same family: an API that documents a parameter as a *directory* will silently misbehave if handed a URL that still carries a query string or fragment, because the string-level manipulation used to derive the parent (`deletingLastPathComponent` and friends) operates on the whole thing including the query.

**How to check**: Whenever a framework-provided URL passes through a decompose/reassemble step (`URLComponents(url:resolvingAgainstBaseURL:)`, manual string joins, serialization to and from a query parameter), verify the result still has a scheme and an absolute path — and prefer building from a plain path string (`bundlePath` + `URL(fileURLWithPath:)`) over transforming a possibly-composite URL. For any API expecting a directory or a bare path, strip query/fragment first (use `.path`, then rebuild) rather than assuming the URL you have is clean. When a URL-consuming API fails with an opaque error, print the URL's `scheme`, `baseURL`, and `absoluteString` separately — the composite structure is invisible in ordinary logging.

**Concrete example (zh-cn-to-tw-mac, `ContentView.swift` / `WebView.swift`, 2026-08-11)**: `Bundle.main.resourceURL` returned a URL internally composed of a relative string plus a baseURL. Passing it through `URLComponents(url:resolvingAgainstBaseURL: false)` while appending query items dropped the baseURL, producing a scheme-less relative URL that `WKWebView` rejected with `WebKitErrorDomain code 101` ("無法顯示URL") and a blank page. Fixed by constructing the path from `Bundle.main.bundlePath` (a plain `String`) via `URL(fileURLWithPath:)`. Independently, `loadFileURL(_:allowingReadAccessTo:)` was being given a "directory" derived from a URL that still had `?desktop=1&...` attached, so the read-access grant was malformed and the load failed silently; fixed by taking `url.path` first to strip the query, then `deletingLastPathComponent()`.

### 10. Under `file://`, page JavaScript cannot read sibling files by any mechanism

**Pattern**: A desktop shell embeds a web UI and loads it from the local filesystem. Any runtime attempt by that page's JavaScript to read another local file fails — and it fails through *every* available API, for different reasons each time, which is what makes it a time sink: `fetch()` is prohibited against `file://` by specification; `XMLHttpRequest` is blocked by the embedding web view regardless of what general web folklore says about XHR and local files; and a hidden `<iframe>` plus `contentDocument` returns `null` because each local file is treated as its own opaque origin for document access. The read-access grant a shell gives the web view (e.g. `allowingReadAccessTo` over a directory) covers the *engine's own* resource loading, not JavaScript-initiated requests, so it does not help. The lesson is structural: under `file://`, treat "JS reads a local file at runtime" as unavailable rather than as an API-selection problem, and reach for a mechanism that isn't a JS-initiated request at all — a `<script src>`-loaded generated file (which travels the engine's resource pipeline), content injected at build time, content pushed in by the host via a JS-evaluation bridge, or an HTTP endpoint.

**How to check**: In any `file://`-loaded page, grep for runtime reads of local resources (`fetch(`, `XMLHttpRequest`, iframe `contentDocument`/`contentWindow` access) against relative paths, and confirm each has a non-JS-initiated path or a server behind it. When adding a "just read this small text file" feature to an embedded UI, decide up front whether the page will ever run from `file://`; if so, don't design around a runtime read. Also verify the same code still works in plain-browser mode if the project ships both, rather than special-casing one and silently breaking the other.

**Concrete example (zh-cn-to-tw-web / zh-cn-to-tw-mac, 2026-08-11)**: A plain-text notice file sat next to `index.html` in the app bundle and was loaded with `fetch("teacher-notice.txt")`. After the shell moved from serving the UI over local HTTP to loading it from `file://`, the panel showed "（載入失敗）". Three successive fixes were attempted and each was disproven by direct testing: `XMLHttpRequest` (its `onerror` fired), then a hidden `<iframe>` (`contentDocument` was `null`, confirmed with explicit logging), then build-time injection into a generated `<script src>` file — which did work, but was rejected as over-complicated because it made a one-file edit require a rebuild. The design was ultimately settled by serving the text from an existing no-auth backend endpoint, so the browser build and the desktop build share one path and editing the file needs no repackaging.

### 11. `file://` pages send a literal `"null"` Origin, which CORS allowlists don't match

**Pattern**: When a page loaded from `file://` makes a cross-origin request, the `Origin` header is the four-character string `null` — not absent, not an empty string, and not anything resembling a URL. Allowlists written as a set of URLs plus localhost patterns therefore reject every request from a desktop shell that loads its UI from the filesystem, including requests to a service running on the very same machine. The symptom is a CORS rejection *despite the server having answered successfully* (the response arrives with a 200 and the browser discards it), which reads as a server problem rather than a configuration one. It also tends to be fixed in only one place: a project with several services will have the origin added to whichever one was being debugged, leaving the others to fail later under the same cause.

**How to check**: If any client loads its pages from `file://`, confirm `"null"` appears in the CORS origin allowlist of **every** service that client calls — remote *and* loopback. Enumerate the services from the client's code rather than from memory. Verify with a preflight rather than by reading config: `curl -i -X OPTIONS <url> -H "Origin: null" -H "Access-Control-Request-Method: POST"` should return `Access-Control-Allow-Origin: null`. Note that adding `"null"` weakens the allowlist meaningfully for internet-facing services (any local HTML file can then call them), so pair it with real authentication on those endpoints instead of relying on origin checks.

**Concrete example (zh-cn-to-tw-backend / zh-cn-to-tw-ocr-service, 2026-08-11)**: After the Mac shell switched to loading its UI via `file://`, `"null"` was added to the Render backend's Flask-CORS origins, but the *local* OCR service's identical allowlist was overlooked — its source comment even predicted the change ("之後如果改成殼直接內嵌網頁資源，origin 會變成 file://，屆時要再加一條") without it being acted on. Uploading a PDF failed with `Origin null is not allowed by Access-Control-Allow-Origin. Status code: 200` — the 200 showing the service had processed the request fine. Fixed by adding `"null"` to the local service's origins as well, verified with an `OPTIONS` preflight returning `Access-Control-Allow-Origin: null`.

### 12. A dynamically-assigned port in the page's origin silently discards all persisted browser state

**Pattern**: Browser storage — `localStorage`, `sessionStorage`, IndexedDB, cookies, service-worker registrations — is partitioned by origin, and an origin is `scheme + host + **port**`. So a desktop app that serves its UI from a locally-spawned server on an OS-assigned ephemeral port gets a *different origin on every launch*, and therefore a completely empty storage area each time, while the previous launches' data accumulates invisibly on disk. The user-visible symptom is not an error but an inexplicable amnesia — most commonly being forced to log in again at every start — and it resists debugging because the storage code is correct, the write succeeds, and reading it back within the same session works fine. Choosing a random port is itself usually a *good* decision (it avoids collisions and stale processes squatting a fixed port); the mistake is letting that port participate in the origin of anything that needs to persist.

**How to check**: For any locally-hosted UI, determine whether its origin is stable across restarts. If a dynamic port is involved anywhere in the URL the user's content is loaded from, anything stored per-origin will be discarded every launch — either pin the port, or load the UI from an origin that doesn't contain one (a fixed `file://` path, a custom scheme, or a registered app scheme). Confirm empirically rather than by reasoning: restart the app several times and look at the on-disk storage directory for the app — multiple sibling per-origin folders accumulating is the signature. Separately, if the port must stay dynamic for the *API* it talks to, ensure that port is not baked into the page's own URL (see item #4).

**Concrete example (zh-cn-to-tw-mac, 2026-08-11)**: The Mac shell originally ran a local backend to serve the web UI over HTTP on an OS-assigned port, so the web view's origin changed on every launch. The application-owned session token stored in `localStorage` was therefore unreachable at the next start, and the user was made to log in again every single time — this was the report that ultimately prompted the whole architecture change. Inspection found three separate `LocalStorage` directories accumulated under the same bundle id, one per distinct port. Fixed by embedding the web assets in the app bundle and loading them from a fixed `file://` path, which is stable for a given installation, and removing the local HTTP server entirely.

### 13. `print`/`stdout` is fully buffered when it isn't a terminal, so diagnostics vanish

**Pattern**: Standard output is line-buffered when attached to a TTY but **fully** buffered (typically 4–8 KB) when redirected to a pipe or file. Code that prints diagnostics therefore behaves completely differently depending on how it was launched: run interactively it prints as expected; run under a supervisor, a log redirect, or a parent process reading its pipe, the output sits in the buffer and appears only when the buffer fills — or never, if the process is killed or `_exit`s. The consequence is worse than missing logs: an investigator concludes the code path *didn't execute*, and goes looking for a nonexistent control-flow bug. This affects every language with buffered stdio (`printf` in C, Swift's `print`, Python without `flush=True` or `-u`), and it can also silently disable a working log-forwarding feature the moment the launch method changes.

**How to check**: For any process whose output is captured by something other than a terminal — subprocesses read via pipes, services under a supervisor, anything with output redirected to a file — confirm it either disables buffering at startup (`setvbuf(stdout, nil, _IONBF, 0)`, `PYTHONUNBUFFERED=1`, `python -u`) or flushes explicitly on every diagnostic write (`flush=True`). Pay particular attention to the *first* line a child writes if a parent parses it as a handshake, and to last-gasp messages before `_exit`/`abort`, which bypass buffer flushing entirely. If a print statement "doesn't run," verify buffering before investigating the logic.

**Concrete example (zh-cn-to-tw-mac / zh-cn-to-tw-ocr-service, 2026-08-11)**: While debugging a blank web view, freshly added Swift `print()` diagnostics produced nothing when the app was launched with stdout redirected to a file, which briefly suggested the code wasn't reached. The cause was full buffering on a non-TTY stdout; `setvbuf(stdout, nil, _IONBF, 0)` in `applicationDidFinishLaunching` made the output appear immediately and unblocked the real investigation. This likely had been silently degrading the app's existing JS-console-forwarding feature all along. On the Python side the same class of problem was already handled deliberately in two places: the child prints its assigned port with `flush=True` (the parent parses that line as a handshake and would otherwise hang), and a watchdog's final message before `os._exit(0)` is wrapped in a `try/except OSError` because the parent's end of the pipe may already be gone.

### 14. Background jobs held only in memory appear "running" forever after the process restarts

**Pattern**: A server tracks background work in an in-process structure and exposes its status for clients to poll. When the process restarts — a deploy, a crash, a platform migrating the instance — the worker threads are gone but the client has no way to learn that. If status is stored only in memory, the job vanishes and polling returns "not found," which clients often treat as an error or, worse, as "your work was lost." If status *is* persisted but nothing reconciles it at startup, the stored row still says `running` and the client polls a job that no thread will ever advance: a silent hang with a progress indicator, which is worse than an error because nothing signals that user action is needed. The critical insight is that persistence alone is not the fix — a restart must actively reconcile "rows claiming to be in progress" against "work this fresh process is actually doing," which by definition is none.

**How to check**: For any long-running background job with a polled status, ask what a client sees if the server restarts mid-job. Confirm (a) status survives restart, and (b) startup marks any still-`pending`/`running` records as interrupted, since a newly started process cannot by definition be executing them. Then check the client: does it distinguish "interrupted" from "failed" and from "not found," and does it offer the user an explicit choice — retry, or finalize with whatever partial results exist? Also check that partial results are saved incrementally rather than only at completion, so an interruption doesn't discard work that was already paid for. Beware of doing the reconciliation query synchronously at import/startup on a cold database — put it on a background thread so it can't delay the server accepting connections.

**Concrete example (zh-cn-to-tw-backend, `db_utils/job_store.py`, 2026-08-11)**: Jobs and reviews lived only in `job_manager`/`review_manager` in-memory dicts, so a Render deploy or instance migration silently destroyed in-flight work — including work whose LLM cost had already been incurred. Fixed by persisting job state to Postgres with memory as the read path and the database as the write path (to keep a ~1.5 s poll cadence off the database), saving partial results after each batch, and adding `mark_running_as_interrupted()` on startup so orphaned rows become `interrupted` instead of perpetually `running`. Without that last step the frontend showed "執行中" forever with no worker behind it. The frontend gained an explicit dialog offering 「重試」 or 「結束此階段工作」, plus `/finalize` endpoints to keep partial output, and the startup reconciliation runs on a background thread because the Neon cold start can approach 10 seconds.

### 15. An idle timeout whose definition of "idle" excludes most of what the user is actually doing

**Pattern**: A component shuts itself down after N minutes without activity, where "activity" is measured by a single narrow signal — typically requests to that component alone. If the user's real workflow involves long stretches of legitimate work that don't touch that component (other stages of the same task, reading, editing, using a different service), the timer keeps counting while the user is fully engaged, and the component disappears from under them. The user's mental model ("I was using the app the whole time, and I refreshed a minute ago") and the code's model ("nothing called *me* for 30 minutes") disagree completely, which makes the resulting bug report sound impossible. Note this is orthogonal to whether shutting down is a good idea — it usually is (see item #5); the defect is the mismatch between the measured signal and the user-facing concept it is standing in for.

**How to check**: For every idle/expiry timer, write down precisely which events reset it, then walk a realistic end-to-end user session and mark which steps do *not*. If a plausible session spends longer than the timeout in steps that don't reset it, either broaden the signal, or — better — make shutdown safe and invisible by ensuring the next use transparently restarts the component and any cached endpoint is refreshed (items #4 and #5). Also confirm the timer cannot fire while work is genuinely in flight: checking "no recent requests" is not the same as checking "no running job," since a long task with no one polling it looks identical to idleness. Explicitly decide whether results already computed but not yet collected are protected.

**Concrete example (zh-cn-to-tw-ocr-service, 2026-08-11)**: The OCR service self-terminated after 30 minutes without HTTP requests *to itself*. But refreshing the page, logging in, Stage 1 refinement, Stage 2 proofreading, and downloading results all go to a different backend, so a user working continuously for hours reset the timer only while an OCR run was actually in progress. The user reported that the service was dead despite having refreshed the UI one minute earlier — which was entirely consistent, since a page refresh never touches that service. One hazard had already been handled correctly: `_idle_watchdog` checks `_has_running_job()` and refuses to exit while any job is `running`, so a long OCR of a large PDF with no one polling is not killed — though results that are finished but not yet retrieved are protected only by a separate 15-minute retention window, not by the idle check.

### 16. A process-wide lock held across an unbounded remote operation

**Pattern**: A single global mutex serializes access to some shared resource, and the critical section contains a *network* operation — opening a database connection, an HTTP call, an RPC, a cloud-storage read. This is usually not written that way on purpose; it arrives by drift. The lock is introduced when the guarded operation is local, fast, and incapable of hanging (a file open, an in-process cache), where a coarse lock is a perfectly reasonable simplification. Later the backing store moves somewhere remote, the *shape* of the code doesn't change — same `with lock:`, same `connect()` — and nobody re-examines the critical section, because the diff that moved it looks like a configuration change, not a concurrency change. Now every transient network hiccup inside that section is no longer slow for one caller; it is a **total freeze of every code path that needs the lock**. If the remote call additionally has no timeout (the default for most clients), a single stuck attempt holds the lock for minutes, and the service is wedged with no error, no crash, and no log line.

Two amplifiers make this much worse and should be checked alongside it. First, **connect-per-operation**: if each guarded operation opens a fresh remote connection rather than reusing a pooled one, the lock is held for a full connection setup on *every* query, so contention scales with traffic even when nothing is broken. Second, and most insidious, **the observation path contending with the work path**: if progress-reporting requests (a status poll, a dashboard, a health page) also take the lock, then watching a long-running job competes with the job itself — the more closely a user monitors it, the slower it goes, which produces the maddening report that a task "only stalls when I'm looking at it."

Note this is *not* a deadlock, and looking for one will waste time: there is a single lock, no cycle, and no lock-ordering bug. The holder is simply blocked, and everyone else is correctly queued behind it. Chasing acquisition order finds nothing.

**The check is "does a lock wrap network I/O", NOT "is a connection pool being used" — do not read this item as evidence against pooling.** This distinction was added in 2026-08-25 because the item as originally written was actively steering readers toward the wrong conclusion. Item 17 below records that `psycopg2.pool.ThreadedConnectionPool` reproduces this exact pathology, and the concrete example in this project ended by removing pooling entirely in favour of a semaphore. Read together, the two items give the strong impression that connection pools are inherently unsafe. They are not. `ThreadedConnectionPool` guards *checkout* and *new-connection creation* with one and the same lock, so `connect()` runs while that lock is held — that is an implementation defect of that specific pool, not a property of pooling. psycopg3's `ConnectionPool` was explicitly designed against it: connections are created by **background workers**, never by the thread requesting one, so the requester only ever waits on a queue and no lock spans network I/O. Its own documentation states the reverse case too — setting background workers to 0 degrades the pool precisely because connection creation then happens in, and blocks, the requesting thread. So a pool is not the diagnostic signal; a lock around an unbounded remote call is. Rejecting a correct pool because of this item is the failure mode to avoid, and it nearly happened here: the semaphore design that replaced pooling is sound, but it accepted a per-request 1.2–1.6 s handshake as unavoidable when the real problem had been the pool's locking, not pooling itself.

**Companion risk when pooling against a serverless/auto-suspending database.** Pools and scale-to-zero backends interact badly in a way that is easy to misdiagnose as "the pool is broken again" — which then feeds the wrong conclusion above. Two distinct hazards: (a) the server closes idle connections unilaterally (Neon's free plan suspends compute after 5 minutes and cannot be configured otherwise), and a pool with no liveness check will happily hand out a dead connection whose failure surfaces later, at query time, far from the cause — set an explicit pre-handout check (psycopg3: `check=ConnectionPool.check_connection`) and keep `max_idle` below the server's suspend threshold so the pool retires connections before the server does. (b) A non-zero `min_size` is worse than merely wasteful on such a backend: the pool's background workers actively *maintain* the floor, so every server-side suspend is immediately followed by a reconnect that wakes the compute again — a permanent keep-alive loop. Against a metered free tier this is a billing failure, not a performance one (Neon's free plan includes 100 CU-hours/month ≈ 0.25 CU for ~400 hours, while a month is ~744 hours, so round-the-clock keep-alive exhausts the quota mid-cycle and the compute is disabled until the next billing period). On any auto-suspending, metered backend, `min_size=0` is the default to reason *away* from, not toward.

**How to check**: Grep for every mutex/critical section and read what is *inside* it — specifically, does the body perform I/O that can block on a network? Any `connect()`, `requests.*`, `fetch`, RPC stub call, or object-store read inside a lock is the bug, regardless of how fast it is on a good day. For each one: (a) does the remote call set an explicit timeout (`connect_timeout`, request timeout, socket deadline)? Unbounded is the difference between "slow" and "hung forever". (b) Does the lock actually need to exist, or was it protecting a constraint of a *previous* implementation? Serializing access is mandatory for some local stores and unnecessary for a server that handles concurrency itself — when the backing store changes, the lock's justification must be re-derived, not inherited. (c) Is a new connection established per operation while holding the lock? (Note the question is whether *creation* happens under the lock — not whether a pool exists. If a pool is in use, read its checkout/creation path and check whether creation is lock-free; see the paragraphs above and item 17.) (d) Do read-only status/progress/health endpoints share the lock with the workers they report on? (e) If the fix removes pooling or lowers concurrency, check what else that mechanism was providing before deleting it — item 18 covers this, and it is how the semaphore in this project's example came to be.

The diagnostic signature is worth memorizing because it identifies this precisely and quickly: an endpoint that touches nothing external stays fast (hundreds of ms) while **every** endpoint touching the dependency times out — *and the dependency itself reports no inbound connections*. That third fact is the decisive one: it proves the requests never reached the dependency at all, so the dependency is not slow and is not out of capacity; the requests are queued inside your own process. Check it directly (`pg_stat_activity`, the service's connection metrics) before concluding the remote system is at fault.

**Concrete example (zh-cn-to-tw-backend, `db_utils/connection.py`, 2026-08-12)**: A single module-level `LOCK = threading.Lock()` guarded all 29 database call sites across `auth_utils`, `admin_utils`, `usage`, and `db_utils`, and each critical section called `psycopg2.connect(DATABASE_URL)` — a fresh TLS connection to a remote Neon Postgres, measured at ~1.6 s per connection — with **no `connect_timeout`**. During a long OCR/refinement run, batches stalled for minutes at a time. Measurements: `/api/health` (no database) answered in **0.10 s**, while `/api/jobs/active` (one trivial `COUNT`) timed out at **30 s on three consecutive attempts**, and `pg_stat_activity` on Neon showed **zero** connections from the backend against a 901 limit — proving the requests were stuck on the in-process lock, never reaching the database. The observation path was the main aggravator: the frontend polls job progress every 1.5 s, and `require_auth` performed *two* separate locked round trips per request (`resolve_session`, then `is_permitted_user`), so simply watching the progress bar competed with the worker thread that needed the same lock to persist each batch. It is tempting to write this off as a leftover from an earlier SQLite implementation, but git showed the commit that introduced the lock *already* contained `psycopg2.connect()` under a `USE_POSTGRES` branch — the remote call was inside the lock from day one, and removing SQLite would not have fixed anything.

**Follow-up that reframes this example (2026-08-25):** the ~1.6 s connection cost treated as a fixed premise throughout the above — and quoted as the justification for the semaphore, for several caches, and for two later optimization plans — turned out to be **99% cross-region deployment**, not a property of the database. Co-locating Render and Neon cut it to ~0.03 s. The lock analysis here was correct and the fix was right; the *attribution of the cost* was not. Before treating any stable, expensive per-operation cost as a premise to design around, run item 25's ratio test first.

### 17. A pool/cache whose own internal lock still wraps the unbounded operation it exists to avoid

> **Scope note (added 2026-08-25):** this item is about *auditing a specific pool implementation*, not about avoiding pools. The instinct it examines — "reuse connections instead of paying the handshake every call" — is correct, and the concrete example below (removing pooling for a semaphore) fixed the freeze but left the per-call handshake cost in place. A pool whose creation path is provably lock-free (psycopg3's `ConnectionPool`, which creates connections on background workers) satisfies both this item and item 16. See item 16's "The check is..." paragraph before concluding anything from this one.

**Pattern**: After diagnosing item 16 (a global lock wrapping an unbounded network call), the natural next instinct is "add a connection pool so we stop paying the connection-setup cost on every call." This is the right instinct but a dangerously easy trap: most off-the-shelf thread-safe pool implementations protect their *entire* checkout/checkin bookkeeping with one internal lock, and — critically — when the pool needs to *grow* (no idle connection available, under the max), it creates that new connection *while still holding its own lock*. The result is structurally identical to the bug just fixed, just relocated one layer down and much harder to spot in review, because the offending lock is inside a well-known library, not in application code that gets read carefully. One slow or hanging new-connection attempt (a backing store cold-starting, a network blip) freezes not just the thread waiting for a *new* connection, but every other thread trying to do anything with the pool at all — including threads that only want to *return* a connection they already finished with. A pool that looks like the fix can be a worse version of the disease: it adds a second lock-acquisition point (the pool's own) on top of removing the first, and unlike application code, its locking behavior isn't visible without reading the library's source.

**How to check**: Before adopting any thread-safe pool/cache for a resource whose creation involves network I/O, read the source of its checkout (`getconn`/`acquire`/`borrow`) and checkin (`putconn`/`release`/`return`) paths and answer: does creating a *new* resource (the cold-miss path) happen while the pool's own lock is held? If yes, a single stuck creation serializes the entire pool, not just the caller who triggered it — treat this as disqualifying for any resource whose creation can be slow or can hang (which includes essentially all remote connections), unless the library explicitly documents that creation happens outside its lock. Confirm empirically before trusting it in production: run a realistic concurrent load test (num threads > pool's warm capacity, so at least one thread must trigger creation) against the *real* backing service, not a local stand-in — a local Postgres/Redis will create new connections fast enough that this bug never manifests in dev, and it will only surface against a backend with real network latency or the possibility of a slow cold start (exactly the conditions a managed free-tier database like Neon reproduces reliably). Watch for a asymmetric completion pattern as the signature: a handful of requests finish (however many connections could be established before contention), then everything else stalls indefinitely — as opposed to uniform slowness, which would suggest ordinary contention rather than a stuck holder blocking everyone.

If avoiding pooling entirely is viable for the traffic volume (true for low-traffic internal tools), the simplest fix that cannot reproduce this failure mode is to not share a lock across concurrent connection attempts at all: let every call open and close its own connection independently, with a timeout so a hang degrades to a bounded per-call failure instead of a global one. This trades a per-call connection-setup cost for the structural guarantee that no caller's slow network operation can ever block any other caller. If pooling is later justified by real load, pick or write one where the creation path is provably lock-free (e.g., a lock only around a queue of *already-established* connections, with new-connection creation happening outside any shared lock, accepting the resulting possibility of transient over-creation).

**Concrete example (zh-cn-to-tw-backend, `db_utils/connection.py`, 2026-08-12)**: Immediately after removing the global `LOCK` from item 16, `psycopg2.pool.ThreadedConnectionPool` was adopted to amortize the ~1.2–1.6 s Neon connection cost. `ThreadedConnectionPool.getconn()` wraps `self._lock.acquire()`/`release()` around `_getconn()`, which calls `self._connect()` — a synchronous `psycopg2.connect()` — whenever the free list is empty and the pool hasn't hit `maxconn`; `putconn()` acquires the *same* `self._lock`. Under a 10-way concurrent test (fresh process, `minconn=1`), the connections that needed to be newly created were serialized one at a time under that lock; measured, only the second thread to acquire a connection ever completed (at 12.08 s) and the remaining nine never completed even after 90+ seconds of continuous observation — i.e., the pool didn't just slow things down, it wedged completely, with the same "several requests finish, everything else stalls forever" signature that item 16 originally produced. (A separate, compounding bug was found in the same attempt: the module's own lazy pool-initialization — `if _pool is None: _pool = ThreadedConnectionPool(...)` — was itself unguarded, so concurrent first calls could each construct a distinct pool instance and race to overwrite the shared global, leaving some connections checked out from a pool object that was no longer the one referenced by `close()`, producing `psycopg2.pool.PoolError: trying to put unkeyed connection`. This is captured separately because it's item 16's exact lazy-singleton failure mode in miniature, but it was subsumed by the larger decision to abandon pooling rather than fix it in place.) The fix was to abandon the pool entirely: every call opens and closes an independent `psycopg2.connect(DATABASE_URL, connect_timeout=10)`, verified afterward with the same 10-concurrent-request test completing uniformly around 1.6 s each — true parallelism, no serialization, no wedge.

### 18. Removing a harmful mechanism without checking what else it was silently doing

**Pattern**: A mechanism is identified as the cause of a problem and removed — correctly, based on solid evidence. But the mechanism was also providing a *second*, undocumented service that nobody attributed to it, because that service was invisible while it worked. Removing the mechanism fixes the diagnosed problem and simultaneously introduces a new failure mode that looks unrelated, often appearing later and under different conditions, which makes it hard to connect back to the change. The classic instance is a lock or queue whose stated purpose is mutual exclusion but whose *de facto* purpose also includes backpressure: by admitting one operation at a time it was, incidentally, capping resource consumption. Delete it and the correctness problem it caused disappears — along with the ceiling that was keeping memory, connections, file handles, or CPU within what the host can survive. Other examples of the same shape: a retry limit that also functioned as a rate limiter; a cache that also absorbed duplicate requests; a single-threaded worker that also guaranteed ordering; a synchronous call that also applied natural flow control.

The insight to carry forward is that the framing "should this mechanism exist?" is the wrong question. The right question is "what are *all* the effects this mechanism currently has, and which of them do I still need?" A mechanism can be badly designed for its stated purpose and load-bearing for an unstated one at the same time. When that is true, the fix is usually to replace it with something that preserves the second effect while dropping the first — not to remove it and not to keep it.

**How to check**: Before deleting a lock, queue, limit, cache, timeout, or serialization point, enumerate its side effects independently of its documented intent: does it cap concurrency? bound memory? enforce ordering? deduplicate? rate-limit? throttle a downstream dependency? For each one, ask whether anything else in the system provides that guarantee. If nothing does, you must supply a replacement — and the replacement should be the *narrowest* mechanism that provides just that property. In the concurrency case specifically, this means preferring a semaphore of N to a mutex: a mutex admits one and turns any single stuck holder into a total outage, while a semaphore admits N, so one stuck holder consumes one of N slots and everyone else proceeds. Pair it with a bound on how long an operation may hold a slot (a real timeout on the underlying call), and a bound on how long a caller will wait for a slot — without the second bound, saturation converts the semaphore back into the same unbounded-queue freeze the original lock caused. Finally, size the limit against *measured* peak demand from realistic usage, not a guess, and confirm the deployment target can survive that peak.

**Concrete example (zh-cn-to-tw-backend, `db_utils/connection.py`, 2026-08-12)**: A global `threading.Lock` around every database access was correctly identified (item 16) as the cause of minutes-long, service-wide freezes and removed. What went unnoticed is that admitting exactly one database operation at a time had also been the only thing capping concurrent connections. With it gone, ten simultaneous requests against the deployed instance (Render free tier: 0.1 CPU, 512 MB) took the whole service down with 502s until it restarted on its own — a failure the original design could not have produced. The replacement was a `threading.Semaphore(5)` plus the existing `connect_timeout=10` and a 20-second cap on waiting for a slot: N-way parallelism instead of serialization, a ceiling on resource use, and a bounded worst case in both directions. Verified with 15 concurrent callers — peak in-flight connections capped at exactly 5, all completed, all slots returned. Two process notes worth keeping: the crash was self-inflicted by load-testing *production* rather than the local environment (the same test had already passed locally, so the production run added no information and only risked the user's live work); and the load applied (10 concurrent) exceeded the application's real measured peak (about 5–6 concurrent, arising not from multiple users but from a single poll tick fanning out into several authenticated requests), so the chosen limit was subsequently sized against that measurement rather than against the arbitrary test.

### 19. Verifying user-interaction bugs through a substitute instead of the real wrapper and real gesture

**Pattern**: A bug only reproduces inside a specific runtime wrapper (a native app's embedded webview, a specific browser engine, a packaged build) and only in response to a specific *kind* of user input (a trackpad/mouse momentum scroll, a long-press, a multi-touch gesture, a drag with inertia). Verifying the fix through a substitute — a different browser engine, a bare HTML file opened outside the app, or a programmatic stand-in for the input (`element.scrollTo()`, `dispatchEvent(new WheelEvent(...))`, a synthetic click) — can pass cleanly while the real bug is still present, because the substitute doesn't exercise the exact code path the bug lives in. The result is a false "verified fixed" that survives repeated automated re-testing and only breaks again when a human actually uses the real thing. This is a distinct failure from ordinary insufficient testing: the tests aren't merely incomplete, they are *structurally incapable* of catching this category of bug, no matter how many times they're run or how many values are tried, because the substitute never enters the code path where the defect lives (a compositing/layering decision made only during real gesture-driven scrolling, an engine-specific rendering quirk, a native event-handling difference).

**How to check**: Before declaring a UI/interaction bug fixed, ask two questions. First: does this reproduce specifically inside a native wrapper (Electron, WKWebView, a packaged mobile shell) rather than in a general-purpose browser? If so, testing against a generic browser tab or a raw file opened outside the app is not evidence, no matter how convincing the result looks — rebuild and relaunch the actual packaged app and test there. Second: does the bug involve a *gesture* (momentum/inertial scroll, pinch, swipe, long-press, drag) rather than a discrete state change? If so, a programmatic substitute for that gesture (`scrollTo`, synthetic events, instant jumps) is not equivalent to the real input and will not exercise the engine's real gesture-handling and compositing code paths — it will typically pass even when the real bug is still present, exactly as it did here. When no tool available can drive the real gesture inside the real wrapper, say so explicitly rather than reporting false confidence from a substitute test, and ask the person who can perform the real gesture to verify directly — a "please check with a real trackpad scroll" is a more honest and more useful answer than a green light from a test that structurally cannot catch the bug.

**Concrete example (zh-cn-to-tw-web / zh-cn-to-tw-mac, 2026-08-12)**: A `position: sticky` sidebar was reported as not staying in place while scrolling in the packaged macOS app (WKWebView). A `max-height` fix was verified by injecting `window.scrollTo()` jumps and reading `getBoundingClientRect()` — both in a standalone browser-based preview tool and, after rebuilding, inside the real native app via console-log forwarding — and every test passed cleanly, with the element's `top` correctly settling and holding across three discrete scroll positions, using real notice-box content of the actual length. The user then reported the element still slid away when scrolling with a real mouse/trackpad in the actual running app. The gap: WebKit has a known issue where a `position: sticky` element not promoted to its own compositing layer can fail to track correctly during momentum/inertial scrolling specifically, a code path that `scrollTo()`'s instantaneous jump does not exercise at all — so the automated verification was not merely weak evidence, it was blind to the exact class of bug being investigated. (A `will-change: transform` compositing-layer fix was applied and pushed, but — consistent with this item's point — it has not yet been confirmed against a real trackpad gesture in the real app, and if it turns out not to fix it, the next step is asking the user to inspect via Safari Web Inspector rather than attempting more automated substitutes.)

### 20. macOS's frozen bash 3.2 misparses `$VAR` immediately followed by a multibyte character under a UTF-8 locale, misreported as "unbound variable"

**Pattern**: Apple's system `/bin/bash` on macOS has been frozen at 3.2.57 for well over a decade (Apple stopped shipping newer bash after the GPLv3 license switch). Combined with `set -u` and an interactive shell's UTF-8 locale (`LANG`/`LC_ALL` such as `en_US.UTF-8`, the default for Terminal.app/iTerm), this old bash has a genuine parsing bug: inside a double-quoted string, a `$VAR` expansion immediately followed by a multibyte (non-ASCII, e.g. CJK full-width) character with no separating whitespace or ASCII punctuation can cause bash to misclassify part of the following character's UTF-8 byte sequence as part of the variable name being expanded. The result is a spurious `set -u` failure reported against a mangled variable name (e.g. `VERSION?: unbound variable`) even though the variable was assigned correctly one line earlier — the error message itself is misleading, since the reported name doesn't appear anywhere in the source. This is exceptionally hard to diagnose because the script works perfectly when run in an environment where the shell's locale happens to be unset/`C` (many tool-invoked or automated shells default this way), while it fails for the actual end user in their ordinary Terminal session — "works on my machine, fails on theirs" is the literal symptom, and the reported "unbound variable" name doesn't match any real identifier in the code, sending debugging down the wrong path entirely.

**How to check**: In any bash script that will run on macOS (not Linux, where the system bash is modern and doesn't have this bug) and mixes `set -u` with non-ASCII/localized text in double-quoted strings, grep for a `$VAR` expansion immediately followed by a non-ASCII byte with no intervening whitespace or ASCII character — that adjacency is the trigger, regardless of which variable or which message it appears in. Don't rely on the invoking environment happening to avoid the bug: tool/CI shells frequently have no locale set and will pass cleanly while a real user's UTF-8 terminal fails on the exact same script. The robust fix is to pin `export LC_ALL=C` near the top of the script (right after `set -euo pipefail`) so the script's own bash process never runs the buggy multibyte-aware code path regardless of the caller's shell locale — this does not affect the actual bytes written to stdout/stderr (the terminal, not bash, renders those), so localized/CJK output still displays correctly. Confirm the fix by reproducing under the buggy condition before trusting it: `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 bash script.sh` should fail before the fix and succeed after.

**Concrete example (zh-cn-to-tw-mac, `packaging/build_dmg.sh` / `packaging/build_app.sh`, 2026-08-14)**: `echo "==> 準備 DMG 內容（版本 $VERSION）"` — `$VERSION` immediately followed by the full-width `）` (U+FF09, UTF-8 bytes `EF BC 89`) — worked perfectly when run via the assistant's own tool-invoked bash (no `LANG`/`LC_ALL` set, defaulting to `C`), but failed for the user in their real Terminal session (`en_US.UTF-8`) with `build_mac_dmg.sh: line 32: VERSION?: unbound variable` — despite a `bash -x` trace showing the immediately preceding line (`+ VERSION=1.0`) had assigned the variable correctly. The failure was only confirmed by deliberately reproducing it (`LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 bash build_mac_dmg.sh debug`), which turned a plausible-but-wrong theory (something else was overwriting `VERSION`) into direct evidence of the real cause — `od -c` on the raw file bytes confirmed the source itself was byte-for-byte correct, ruling out file corruption. Fixed by adding `export LC_ALL=C` immediately after `set -euo pipefail` in both `build_app.sh` and `build_dmg.sh`; re-running under the same forced UTF-8 locale afterward completed cleanly with the Chinese status text still displaying correctly.

### 21. A "package for distribution" wrapper script that never re-invokes the actual build step, silently shipping stale content in a freshly-timestamped artifact

**Pattern**: A packaging pipeline is deliberately split into a build step (compile/assemble source into a runnable artifact) and a package step (wrap that already-built artifact into a distributable file — a DMG, an installer, a zip, a container image tag). Splitting them is a reasonable, common optimization: re-running the package step alone (to re-test the install flow, tweak packaging metadata) shouldn't force a full rebuild every time. The trap is a *third*, higher-level entry point meant to be "the one command that does everything" — a top-level wrapper, a Makefile `all` target, a CI job — that in fact only calls the package step and skips the build step, either because it was written by copying the package step's own invocation pattern, or because the split was made at the low level and nobody separately verified the top-level entry point actually chains both stages. The output looks completely trustworthy: the packaged file has a brand-new timestamp, the command exits 0 with no warnings, and re-running it after a source change produces a *different file* — just one with unchanged content, because it repackaged whatever binary/bundle happened to already be sitting in the build-output directory from whenever the build step last actually ran (possibly hours or days earlier, possibly never for that source change). Anyone testing through this entry point after a fix will observe the fix "not working," and the natural next move is to keep digging into the fix's logic — which is a dead end, since the logic was never actually retested.

**How to check**: For every packaging/distribution entry point advertised as (or that reads like) "build and ship this," trace what it actually invokes — not what its name or its comments claim. Confirm it calls the real compile/build step (not just the assemble-and-wrap step) every single time it runs, with no `if [ -d already-built ]` early-exit and no dependence on some other process having built it first. If a lower-level "package only, don't rebuild" script exists for the legitimate re-test-the-install-flow use case, keep it — but make sure the top-level "do everything" entry point does not simply delegate straight to it; it should either force a clean build itself or explicitly call the real build step before delegating to the package-only step. A quick empirical test settles it for any suspect entry point: touch/modify a source file with an obvious, greppable change (a print statement, a version string), run the top-level entry point, and confirm that exact change is present in the installed/unpacked artifact — a passing "it built without error" is not evidence, only inspecting the actual shipped content is.

Two extensions, both learned the hard way (see Concrete example 2). First, **the clean/rebuild scope must cover every input that ends up inside the artifact, not just the code this repo compiles itself.** Enumerate what gets embedded — a sibling repo's PyInstaller/webpack output, a pre-built framework, downloaded model weights, a vendored binary — and for each ask "if its source changed today, what in this pipeline would rebuild it?" Anything that enters the artifact as an *already-built* file is exactly where staleness hides, precisely because it doesn't look like something the build owns. Do not assume a dependency artifact is current just because you didn't build it. Second, **a successful build is not evidence the artifact runs.** Compilers and packagers report success for output that dies instantly at startup (a missing runtime import, a language feature the target interpreter doesn't support, a broken signature). If the artifact is executable, the pipeline should actually start it and confirm one real signal of life — a health endpoint, a version flag, a known line of output — and fail the build if that doesn't come. This costs seconds and is the only thing that distinguishes "packaged" from "works."

**Concrete example (zh-cn-to-tw-mac, `packaging/build_dmg_all.sh` / meta-repo `build_mac_dmg.sh`, 2026-08-16)**: The meta-repo root's `build_mac_dmg.sh` was a git-tracked symlink straight to `build_dmg_all.sh`, which existed to run *both* the 13+ and 12- packaging scripts in one command — but each of those only wraps an already-built `.app` into a DMG (`build_dmg_*.sh` checks `[ ! -d "$APP_BUNDLE" ]` and errors out if missing, but never itself runs `swift build` or re-copies the web frontend source, by design, so repeated DMG-only re-testing doesn't force a rebuild every time). Two rounds of real source fixes (a frontend polling change, then a backend log-streaming fix in a *different* repo bundled into the `.app`'s Resources) were made, and the user's standing workflow — `bash build_mac_dmg.sh debug`, uninstall, reinstall — produced a DMG with a fresh file timestamp each time, but the installed app kept exhibiting the pre-fix behavior, because the `.app` being wrapped hadn't actually been rebuilt since an earlier point in the session; nothing in the pipeline errored or warned about this. The assistant's first explanation — "you must have tested a stale DMG" — was itself an unverified, premature diagnosis (see item on verifying before diagnosing); the real, confirmed cause was that `build_dmg_all.sh` structurally never called the build step at all. Fixed by making `build_dmg_all.sh` call `build_app_13_plus.sh`/`build_app_12_minus.sh` (the real `swift build` + asset-copy step) before packaging each DMG, and by converting the root `build_mac_dmg.sh` from a bare symlink (which cannot inject any "clean first" behavior, being pure filesystem indirection with no logic of its own) into a real script that `rm -rf`s both `.build/` directories before delegating — so the one command the user actually runs is guaranteed to be a genuine clean build, not an incremental one that could theoretically also mask staleness. The lower-level `build_dmg_13_plus.sh`/`build_dmg_12_minus.sh` kept their original "package only" behavior for the legitimate re-test-install-flow case.

**Concrete example 2 (meta-repo `build_mac_dmg.sh` / zh-cn-to-tw-ocr-service, 2026-08-22)**: The fix above was in place and working — `build_mac_dmg.sh` really did `rm -rf` both SwiftPM `.build/` directories and really did chain through to `swift build` — and the same class of bug shipped anyway, because the clean scope covered only what *this* repo compiles. The 11+ `.app` embeds `zh-cn-to-tw-ocr-service`'s **PyInstaller output** (`dist/`), not its source, and nothing in the pipeline ever rebuilt that. The user asked for "latest code, clean build"; `git pull` brought in two same-day ocr-service commits — one of them literally "修正 RapidOCR 偵測門檻太高導致整行文字憑空消失" (the exact user-visible bug being chased that week) — while `dist/` still held a binary built five days earlier. Every stage reported success and the DMG carried a fresh timestamp. Worse, the stale binary would have *silently ignored* the new `box_thresh` parameter the freshly-embedded frontend had just started sending: no error, no warning, just the old threshold and the old missing-lines behavior, which would have read as "the fix didn't work." Caught only because a human pushed back on the idea that a dependency with new commits could legitimately go unrebuilt. Rebuilding `dist/` then exposed the second half: `pyinstaller` printed `Build complete!` and produced an executable that crashed on `import` with `TypeError: unsupported operand type(s) for |: 'type' and 'NoneType'` — a `float | None` (PEP 604) annotation added that day in `ocr_utils/ocr_engine.py`, which needs Python 3.10+ unless the module carries `from __future__ import annotations`, against a 3.9 packaging venv. That file was the only one in the repo missing the future import (`app.py`, `pdf_to_images.py`, `cover_detect.py` all had it); on a 3.10+ dev machine the source runs fine and nothing surfaces until it's frozen, which is why the authoring session never saw it. Fixed on three levels: the missing import; `build_mac_dmg.sh` now rebuilds the ocr-service `dist/` (clearing PyInstaller's `build/` cache too, since `dist/`-only deletion lets it refill from cache) and hard-fails if that repo's own venv is absent rather than silently skipping; and a smoke test that launches the freshly packaged executable, waits for its `OCR_SERVICE_PORT=` handshake line, and curls `/health` — aborting the whole build if either doesn't come. The smoke test was verified by deliberately re-breaking the file and confirming the script exits 1 without ever reaching the DMG stage, rather than by trusting that it would.

### 22. A second native shell reuses a shared frontend's platform-identity tier value and collides with the first platform's real policy data

**Pattern**: A frontend is shared across multiple native shells (a web UI embedded in both a macOS app and a Windows app, for instance), and one call site in that shared frontend hardcodes a platform-identifying literal (e.g. `os=macos`) rather than deriving it dynamically — often because the frontend was written before a second platform existed, and nobody revisited that one literal when the second shell was added. Separately, the shell passes its own "which build/tier am I" value through a query parameter (e.g. `osTier`) that a backend endpoint uses, together with the frontend's hardcoded literal, as a composite lookup key against per-platform policy data (version-gating thresholds, feature flags, anything keyed by `(platform, tier)`). When the second shell is scaffolded, the path of least resistance is to reuse an existing tier value from the *first* platform (it's already known to satisfy whatever string-equality checks exist elsewhere in the shared frontend) instead of registering a new one — but doing so, combined with the frontend's hardcoded platform literal, produces a composite key that is bitwise identical to a key the first platform's real, currently-deployed build actually uses. The backend cannot tell these two callers apart: it correctly answers the query, but the query itself was lying about which platform/build is asking. Symptoms therefore look like backend or business-logic bugs (a forced-update dialog demanding a version that doesn't exist yet for this platform, a feature flag flipping unexpectedly) even though every individual piece of code — the backend's policy lookup, the frontend's hardcoded literal, the shell's reused tier value — is functioning exactly as written.

**How to check**: When scaffolding a second native shell around a frontend originally built for one platform, grep that shared frontend for any hardcoded platform-identifying literal (`os=`, a UA-sniff, a build-tier string) passed to backend endpoints, and treat every one as a landmine for the new shell — not because it needs fixing right now (changing shared frontend code for a not-yet-shipped platform carries its own risk), but because any query-string parameter the new shell controls that co-occurs with that hardcoded literal must not accidentally reconstruct a composite key the first platform's real deployed policy data already uses. Enumerate what composite keys currently exist in the backend's policy store for the first platform, and confirm the new shell's parameter choice cannot produce any of them. When the check has to fail closed (uncertain whether a value collides), prefer an invented tier value guaranteed absent from the policy store over reusing one of the first platform's real tier strings — most such backends are (or should be) designed so "no policy row found" means "don't block," which turns an unregistered value into a safe default rather than an error.

**Concrete example (zh-cn-to-tw-web / zh-cn-to-tw-windows, 2026-08-17)**: `zh-cn-to-tw-web`'s `script.js` calls `GET /api/version_check?os=macos&os_version=${DESKTOP_OS_TIER}` with `os=macos` hardcoded (written before a Windows shell existed). The new Windows shell's `MainWindow.xaml.cs` set its `osTier` query parameter to `"13+"`, reusing the Mac build's tier string specifically to avoid `script.js`'s *other* tier-string check (`STAGE1_LOCKED = DESKTOP_OS_TIER === "12-"`), without noticing that `(os=macos, os_version=13+)` is exactly the composite key the real, currently-shipping Mac build's version policy uses. The backend's `app_versions` table had a row for that key requiring a minimum version of 1.1; the Windows shell's own version reporting was a yet-unwired placeholder (`0.0`/`0.1`), so on first login the user saw "目前 App 版本過舊（最低需求版本 1.1），請先更新才能繼續使用" — a forced-update dialog for a version number the Windows build has no concept of. `app.py`'s `version_check` was already written to return `force_update: false` whenever `get_policy()` finds no row for the given `(os, os_version)` pair ("查無這個 os 的門檻資料時一律不擋"), so the fix was simply to change the Windows shell's `osTier` to `"windows"` — a value with no row in the table — which resolved to the safe "don't block" default and also happens not to match `"12-"`, so it doesn't disturb `script.js`'s other tier-keyed branch either.

### 23. A one-shot loopback socket accept for an OAuth callback loses the race to any extra/spurious connection

**Pattern**: A desktop app's RFC-8252 native-app OAuth flow implements its own minimal loopback HTTP server by calling the platform's "accept one connection" primitive exactly once (`TcpListener.AcceptTcpClientAsync()` called a single time, `NWListener` torn down the instant its first connection's outcome — success *or* failure — is known), then stops listening. This is a reasonable design *if* the real browser's callback POST is guaranteed to be the only connection the server ever sees. In practice a modern browser can open more than one TCP connection to that loopback port around the same navigation for reasons unrelated to the actual callback (connection warm-up, a retried/duplicated tab from an earlier failed attempt still sitting open, etc.), and if any such connection is accepted first, the server's single accept slot is consumed and the listener stops *before* the real, id_token-bearing POST ever arrives — which the browser then sees as an ordinary TCP-level "connection refused," not an application error. The failure is intermittent and looks exactly like a slow/broken OAuth exchange (spinner runs a long time, then a generic failure), which makes a protocol-level misconfiguration (redirect URI mismatch, a missing HTTP handshake step) the natural first suspect — and that's a dead end, because the server-side HTTP parsing was never reached for the connection that mattered.

**How to check**: For any hand-rolled loopback listener written to receive a single OAuth/native-app callback, find where it accepts a connection and confirm whether it accepts *exactly once* versus in a loop that continues until a valid payload is parsed (or the overall flow times out). A single accept is fragile by construction — nothing about the browser or the OS guarantees the first connection to arrive is the one carrying the real callback. Prefer looping accept-and-inspect until the expected payload is found, with the same overall timeout bounding total wait time so a hung flow still terminates. Before trusting any fix in this area, don't reason about it from protocol theory alone (see item 19's point about false confidence from a substitute) — add temporary raw-request logging (headers, and connection source) so you can see, empirically, what the real client actually sent on each accepted connection, since guessed hypotheses about HTTP handshake details can look completely plausible and still be wrong. Any such logging that touches an id_token/access_token/bearer credential must mask the token value before writing to disk (it's a replayable credential bearing real user identity, not inert debug text) — log presence/length, not the raw value.

**Concrete example (zh-cn-to-tw-windows, `GoogleDesktopSignIn.cs`, 2026-08-20)**: Windows desktop Google Sign-In intermittently failed with "登入失敗，沒有取得 id_token" after Google's account-picker spinner ran for 40–70 s, and — once multiple retry attempts had left several stale `127.0.0.1` tabs open in Chrome — new attempts failed almost immediately with Chrome's own `ERR_CONNECTION_REFUSED` page. The first hypothesis (Chrome sending `Expect: 100-continue` before the body, which the hand-rolled server didn't handle) was plausible-sounding, matched the timing, and was implemented — but was directly disproven by adding raw-header logging and capturing an actual Chrome 151 callback request: it carried no `Expect` header at all. The real cause was that `StartAsync()` called `listener.AcceptTcpClientAsync()` exactly once; any connection reaching the port first (confirmed reproducible by manually racing a second, non-callback connection into the port ahead of the real one) consumed that single accept and caused the real form-post — arriving after — to be refused against an already-stopped listener. Fixed by replacing the single accept with a loop that keeps accepting connections, logging each one (with `id_token=...` masked to a length before writing to `%LOCALAPPDATA%\ZhCnToTw\oauth_debug.log`), until one yields a parseable `id_token` or the overall 300 s sign-in timeout elapses; verified against a real Google account after the fix, and the diagnostic log showed the successful run receiving exactly one clean connection with the real token. Mac's `GoogleDesktopSignIn.swift` has the same architectural shape (`NWListener.newConnectionHandler` fires per-connection, but a `didFinish` guard means whichever connection's outcome is determined *first* — success or failure — tears down the listener for every other in-flight connection too) and is therefore a plausible candidate for the identical bug, but no real failure has been observed there in practice (Safari's connection behavior for this flow may simply not trigger the race) — left unchanged pending actual evidence of a Mac-side failure, per this checklist's general preference for fixing what's proven broken over what's theoretically fragile.

### 24. Inferring a general rule from a coincidental pattern in past actions, then extending it without explicit authorization

**Pattern**: This one isn't a code defect — it's an assistant behavior bug, and it destroys user data (or public-facing content) exactly like one. Several past edits to the same file/resource happened to share a visible side effect (e.g., "the last two times we shipped a new version, the old version's entry got removed"). Nothing about *why* that side effect occurred was actually checked — it could have been incidental to those specific situations, driven by some other condition entirely (a policy decision, an explicit one-off instruction, a coincidence of timing) rather than being "the rule" for that action in general. On the next occasion, the assistant pattern-matches on the repeated *appearance* and reproduces it proactively, without the user having asked for that side effect this time — turning an observed correlation into an invented, self-authorized policy. Because the resulting change still "looks like" past changes (same shape of diff, same files touched), it can ship, get reviewed favorably, and go live before anyone notices the underlying justification was never actually true for this instance. The damage is compounding: each repetition that goes unquestioned further cements the false pattern as "how we've always done it," making it *more* convincing evidence to the next context window that never saw the original, real justification.

**How to check**: Before repeating any behavior that removes, overwrites, or destroys something (an old download link, a config value, a history entry, a file) on the grounds that "this is what we did last time" or "this seems to be the convention here," find the *actual causal reason* for the precedent — not just its shape. Read the commit message, ask the user, or check whether a comment in the code documents *why*, not just *that*. If the precedent's real trigger was a specific condition (e.g., "that version was being force-deprecated") and that same condition doesn't independently hold this time, the precedent does not apply — do the additive/non-destructive thing by default, and only destroy/overwrite when the user's *current* instruction says so or the condition that justified it last time is verifiably true again. When a comment in the codebase itself asserts a convention, treat it as a claim to verify against actual git history (who wrote it, when, and why) rather than an unquestionable ground truth — comments can themselves be the artifact of exactly this mistake, written by an earlier session that made the same wrong inference and then documented its own error as if it were policy.

**Concrete example (zh-cn-to-tw-web, `update-page` branch `index.html`, 2026-08-18 to 2026-08-23)**: The download page's Windows and Mac sections were originally designed so every new release added a sibling `.version-block` (`.version-block + .version-block` CSS handles the divider automatically), preserving every past version's download link indefinitely. Over five days and three version bumps (1.2→1.3, 1.3→1.4, and independently on the Windows side again for 1.4→1.5), successive sessions instead *overwrote* the single existing block in place, and along the way even wrote a code comment asserting this was the intended design ("刻意只留目前這一個版本"/"目前刻意不保留，只留最新版") — turning an unauthorized habit into apparent documented policy. The real reason the *first* couple of removals were fine was incidental and never stated in the code: those particular releases happened to be paired with a force-update policy change (`min_version` bumped to match `current_version` in the backend's `app_versions` table), which genuinely retired the old version and made its link pointless — but this was a property of *those specific releases*, not a general rule about shipping a new version. The 1.5 release broke the false pattern: the user explicitly kept `min_version` at 1.4 (1.4 was still fully supported), yet both the Windows-side and Mac-side sessions independently replaced the 1.4 entry with 1.5 anyway, extrapolating from the shape of prior diffs rather than checking why those diffs had looked that way. The user caught it, pointed at the *original* code comment ("之後同一個平台出新版本，就在同一個section裡再加一個.version-block") that both sessions had missed or overridden, and confirmed the actual rule: add, never overwrite, unless explicitly told to remove or unless the version being replaced has genuinely been retired by a force-update decision. Fixed by restoring the removed `.version-block`s and rewriting the misleading comments to state the real conditional rule instead of the false absolute one.

### 25. An expensive per-operation cost optimized inside the application when it is actually deployment topology

**Pattern**: A per-operation cost — connection setup, an API round trip, a cache miss — is measured, found to be large *and stable across repetitions*, and therefore accepted as an inherent property of the operation. Effort then goes into *amortizing* it: pooling, caching, batching, or reducing the number of calls. Every one of those is legitimate work with measurable wins, which is exactly what makes this trap hard to see. The question that never gets asked is why the primitive is expensive in the first place. When the two ends sit in different geographic regions, the answer is that the operation contains almost no computation at all — it is N network round trips, and each round trip is priced by physical distance. Amortization divides that constant; relocation can remove ~98% of it. The asymmetry is what sustains the trap: the amortization path produces code, diffs, benchmarks, and a satisfying optimization narrative, while the topology fix produces no code — it is a dropdown in a console, or a data migration — and so it never presents itself as "the work."

**Diagnostic signature (the decisive test)**: measure *one* round trip in isolation, then divide.

- Get a clean 1-RTT number. Best: a raw TCP handshake (`socket.connect` — SYN → SYN/ACK is exactly one round trip by definition, with no TLS, auth, or query mixed in). Acceptable: a trivial query on an *already-established* connection.
- Divide the expensive operation's cost by that RTT.
- **A quotient landing on a small integer means the operation is pure network round trips and contains essentially no computation.** For a TLS + SCRAM-SHA-256 Postgres connect, expect ≈ 6 (TCP 1 + TLS 1–2 + SCRAM ≈ 3).
- A quotient at the expected integer proves *distance*. A quotient far **above** it means something is adding non-network cost — CPU starvation, scheduler throttling, a proxy — which is a different bug with a different fix.

This single ratio separates "far away" from "slow machine", which are otherwise indistinguishable from the outside and invite months of misdirected optimization.

**How to check**: for every remote dependency, confirm where each end is *actually deployed* — read it from the provider's console or from the connection string itself, do not infer it from the provider's default region, the account's home region, or the latency you happen to observe. Then compare both against where the **users** are, because co-locating the wrong pair optimizes the wrong hop. Do this *before* scoping any work that treats the per-operation cost as fixed. A useful smell test: if a datacenter is slower to reach a dependency than a developer's home broadband is, the topology is wrong regardless of what any dashboard says.

**Concrete example (zh-cn-to-tw, 2026-08-25)**: The backend ran on Render in **Singapore**; the Neon database had been created in **us-east-2 (Ohio)**. `/api/health` (no database) answered in 0.11 s while `/api/jobs/active` — one `COUNT`, one connection, no authentication — took 1.76–1.99 s, and crucially **the fifth consecutive call was still 1.76 s**, ruling out cold starts. A raw TCP handshake to the Neon host measured **199.7 ms** median from Taiwan; a query on a reused connection measured 210.4 ms, so ~10 ms of that was actual query execution and the rest was one round trip. Dividing: 1228 ms connect ÷ 199.7 ms = **6.15 round trips**, matching the predicted 6. Applying the model to production gave ≈236 ms per round trip, consistent with Singapore↔Ohio and inconsistent with Oregon (~65 ms), which also ruled out the competing hypothesis that Render's 0.1 CPU was throttling the crypto-heavy handshake. A telling detail along the way: the production backend was *further* from its own database (~236 ms) than the developer's home broadband in Taiwan was (199.7 ms).

Migrating the database to Singapore (Neon cannot change an existing project's region — you create a new project in the target region and move the data) produced, with `/api/health` subtracted as the baseline: net database cost **1.76 s → 0.03 s, about 59×**; `/api/jobs/active` 1.78–1.99 s → 0.12–0.21 s. Note the **59× measured against a 118× prediction** — the forecast assumed a ~2 ms same-region RTT, and the real figure was ~4.3 ms; record measurements, not forecasts. The freshly created database independently reproduced the ratio (`connect ÷ RTT = 5.98`), so two entirely different network paths both landed on 6, which is what turns this from one coincidence into a reusable test.

The cost of missing this: **two fully-scoped engineering plans had been justified entirely by the 1.2–1.6 s handshake** — a psycopg3 connection-pool migration and a refactor of an authentication path that opened 5 connections per request. Both were real work with real wins, and both dropped from critical to optional the moment the region was known (the pool's remaining benefit fell to ~130 ms per request; the 5→2 connection refactor to ~90 ms). Neither was done. Several source comments across four files had also hardcoded "1.2–1.6 s" as the stated justification for caches and write-throttles; those numbers became wrong by a factor of 59 overnight, so the comments were corrected in place rather than left to mislead the next reader — the mechanisms themselves were kept, because they were doing other things too (see item 18).

**Meta-lesson on how the fact stayed hidden**: the region went unchecked for the entire investigation because the AI session doing the analysis could not see the deployment console, and responded by designing an elaborate in-process timing experiment to *infer* the location. The human operator could read it from a settings page in two clicks. **The constraint being routed around bound only the assistant, not the user.** When a fact is cheap for the user to look up and expensive to infer, ask for it before building the inference.
